# Диагностика для агента: инструменты, вывод и сигналы по приложениям (предложение)

Статус: предложение, не утверждено. Основа — живые прогоны 2026-10-24 (`diag run --profile discord`), три
независимых разбора (взгляд агента в терминале, предметный взгляд DPI/zapret/Discord, схема вывода для LLM) и
осмотр того, что уже есть в коде хаба и в журналах программ на этой машине.

Цель: на жалобу «не работает X» агент запускает одну команду и получает всё, чтобы назвать причину и
исправить, не задавая пользователю лишних вопросов и не лазая по журналам сам.

## 1. Что у хаба уже есть и что из этого брать в вывод

Оценка: **польза** для поиска причины; **цена** — время прогона и код. «В вывод» — как показывать агенту.

| Инструмент (где) | Что даёт | Польза | Цена | В вывод |
|---|---|---|---|---|
| Наблюдение `router::observe` | потоки программы, SNI, SYN без ответа, RST, UDP без ответов | высокая | уже есть | `observed`: число потоков по протоколу/портам, сколько через роутер и через системный прокси; виновники — компактно |
| Журнал Discord `renderer_js.log` | этап, на котором оборвался голос; DAVE; собеседники | очень высокая | дёшево (парсер есть) | `client`: стадия голоса кодом (`no_endpoint`, `ws_failed`, `udp_failed`, `dave_waiting_peer`, `connected`), сервер, число собеседников |
| Журнал Discord `discord-webrtc_0/1` | пинг каждые 5 с с номером, переподключения, пакеты отправлено/получено, ошибки расшифровки, RTT регионов | очень высокая | средне (новый парсер) | `client.voice`: потери и RTT по пингам, односторонний звук, переподключения, лучший регион |
| Журнал Discord `Discord_updater_rCURRENT.log` | обновление не скачивается | средняя (симптом «вечное обновление») | дёшево | `client.updater`: последняя ошибка |
| Журнал NekoBox и `routes_box` | куда NekoBox отправил домен, медленный DNS | высокая | есть, но NekoBox ищется только по имени процесса | искать ещё по процессу на порту системного прокси; `proxy.routes_for_culprits` |
| Быстрая проверка (`quick-check`, `utils\targets.txt`) | HTTP / TLS1.2 / TLS1.3 / ping к целям Flowseal | средняя: фон «работает ли zapret вообще» | ~5–10 с | `baseline`: только упавшие цели + счёт ok/всего |
| DPI 16–20 КБ (`tester::dpi`, набор hyperion-cs) | TCP замирает после 16–20 КБ — признак торможения ТСПУ, которого не видит `curl -I` | высокая для YouTube/Steam/DbD/любого TCP | ~10–20 с на подмножество | `dpi_freeze`: проверено/замерло по провайдерам; провайдера виновника — первым |
| Системные проверки (`checks`) | BFE, конфликтующие программы, прокси, TCP timestamps, VPN, Secure DNS, hosts | средняя | уже в отчёте | только не-Ok, кодом `CheckId` + `action` (команда `checks fix …`) |
| Состояние движка (`status`) | служба, winws/winws2, WinDivert, стратегия, версия Flowseal, есть ли обновление | средняя | дёшево | `engine`: стратегия, служба, движок жив, версия устарела |
| История тестов (`tests`) | рейтинг стратегий по профилю, когда последний прогон | средняя | дёшево | `tests`: место текущей стратегии, лучшая по профилю, возраст прогона |
| Роутер (`routes list`, `routes flows`) | какое правило ловит программу, трафик по правилу | высокая (у вас голос шёл через правило) | дёшево | `routing`: включён/на паузе, правила, совпавшие с виновниками, байты туда/обратно |
| Прокси (`probe::socks`, `nekobox_port`, `listening`) | жив ли SOCKS5, порт NekoBox, внешний IP | высокая | дёшево | `proxy`: адрес, жив, **умеет ли UDP ASSOCIATE**, внешний IP через прокси |
| Списки (`lists`, `ipset`, hostlist стратегии, `game-filter`, `hosts`) | покрыт ли виновник стратегией; возраст списков; порты игрового фильтра | высокая (устаревший список = частая причина) | дёшево | `coverage`: виновник в hostlist/ipset да/нет, порты фильтра покрывают порт виновника, возраст списков, запись в hosts |
| DNS (`dns_udp` против DoH) | подмена DNS | средняя | есть | `dns`: подменённые имена |
| Пробы путей (`paths` + `evaluate`) | что из путей лечит | высокая, когда сломано | минуты | `best_paths` компактно; по пробам — разбивка |
| Журнал хаба `data\logs` | ошибки самого хаба (WinDivert, службы) | средняя (вчерашний сбой WinDivert нашёлся только так) | дёшево | `hub_errors`: последние ошибки за сутки, кодом |
| Очистка кэша Discord (`discord clear-cache`) | исправление «Discord не грузится после обновления» | низкая | — | только как `next_steps`, если стадия `no_endpoint` и шлюз отвечает |

Чего у хаба нет совсем и что дёшево добавить: проба голосового WebSocket и шлюза Discord (`wss`), долгая проба
UDP (~40 пакетов IP Discovery за 4 с), замер пропускной способности TCP (скачать 100–500 КБ с реального CDN),
RTT пути для игр (ICMP/UDP до сервера матча), проверка UDP через SOCKS5.

## 2. Как сделать вывод удобным агенту

Принципы:

1. **Ответ сверху, детали ниже.** Первые 15 строк JSON решают: что случилось, насколько уверены, что делать.
2. **Коды отдельно от текста.** Английские стабильные коды (`verdict.code`, `evidence[].code`) + русский
   `text` для пользователя. Агент ветвится по кодам, пересказывает текст.
3. **Только аномалии.** «Ok» не печатаются (счёт — да). Повторы (текст стратегии в каждом пути,
   `representatives` = `members`) убираются.
4. **Каждое действие — готовая команда.** `fixes[].cli`, `next_steps[]` — точные строки `zapret-hub-cli …`
   или вопрос пользователю с командой повтора.
5. **Уверенность с причинами.** `confidence: high|medium|low` + `why: [codes]` по правилам: остановлен,
   вышел бюджет, нет источников, голосового потока не было, лучший путь прошёл на пороге 2 из 3.
6. **Проверяемые улики.** `evidence[]` — коротко и с адресом/строкой журнала, чтобы агент мог перепроверить.
7. **Компактно по умолчанию, полностью по `--full`.** Компактный вид строит CLI из того же `Summary`; окно
   приложения не меняется. Ход прогона — по строкам в stderr (как сейчас) и по желанию `--progress jsonl`.
8. **Отказ раньше наблюдения.** Discord не запущен / не в голосе → сразу `verdict.code = not_reproducible`
   и `next_steps: ask_user "зайдите в голосовой канал", затем команда повтора`.

## 3. Сигналы по приложениям

Для каждого: типичные причины в России, что хаб должен собрать, чем отличить причины.

### Discord, голос
- Причины: UDP 50000+ / 19294–19344 режется; голосовой WebSocket (`*.discord.media`) не открывается;
  NekoBox или правило ведут голос мимо/через VPN без UDP; DAVE ждёт собеседника; сбой у собеседника;
  плохой регион.
- Собрать: стадию из `renderer_js.log`; пинги/потери/RTT/переподключения/отправлено-получено из
  `discord-webrtc_0`; долгую пробу IP Discovery «как сейчас»; пробу `wss` к серверу из журнала напрямую и
  через прокси; умеет ли прокси UDP; правило роутера/NekoBox для `discord.media`.
- Отличить: `no_endpoint` → шлюз/аккаунт; `ws_failed` → TCP/TLS к `discord.media`; `udp_failed` → UDP
  (тут и нужен перебор путей); `dave_waiting_peer` один в канале → не сбой; получено ≈ 0 при отправлено > 0 у
  одного собеседника → его сторона.
- Исправить уже: правило «один в канале + DAVE не стартовал = наш сбой» (ложно); признак «потери» на тихом
  голосе (ложно).

### Discord, видео и демонстрация (Go Live)
- Отдельное соединение `Connection(stream)` к своим серверам (в журнале — 35.217.x:500xx); битрейт выше,
  поэтому торможение «после N пакетов» бьёт сюда первым.
- Собрать: стадию и счётчики соединения `stream` отдельно от голоса; долгую пробу UDP большими пакетами;
  отправлено/получено и переподключения потока.
- В выводе: `client.stream` рядом с `client.voice`; виновник помечается `kind: stream`, не `voice`.
  Отдельный профиль `discord-stream` или ключ `--what voice|stream`.

### Discord, приложение, текст, обновления
- Причины: шлюз `gateway*.discord.gg`, `discord.com` API, CDN `cdn.discordapp.com`/`media.discordapp.net`,
  обновления `updates.discord.com`/`dl*.discordapp.net`; устаревший hostlist.
- Собрать: стадию шлюза из журнала (`[CONNECT]` без `[CONNECTED]`); ошибку из журнала обновлятора;
  покрытие этих доменов hostlist стратегии; DPI 16–20 КБ на CDN.

### YouTube
- Причины: торможение googlevideo по TCP (замирание после 16–20 КБ), блок QUIC (UDP 443), подмена DNS,
  запись в hosts, браузерный DoH в обход zapret, устаревшие списки.
- Собрать: потоки браузера к `*.googlevideo.com` — байты и паузы по времени (скорость, а не «ответил»);
  DPI 16–20 КБ; замер скачивания 500 КБ с googlevideo-хоста виновника по пути; QUIC против TCP;
  `HostsYoutube` и Secure DNS из системных проверок; покрытие списками.
- Отличить: TCP замирает → торможение (нужен приём против 16–20 КБ); QUIC не отвечает, TCP идёт → блок QUIC
  (браузер сам откатится, но медленно); DNS подменён → DNS.

### Steam
- Причины: `steamcommunity.com` и часть магазина режутся по TLS; CM-серверы (`*.steamserver.net`,
  websocket, 27015–27050); загрузки CDN (`*.steamcontent.com`, Akamai) тормозятся; маршрут через VPN
  ломает регион.
- Собрать: журналы Steam (путь из `HKCU\Software\Valve\Steam\SteamPath`, `logs\`):
  `connection_log.txt` (подключения к CM и их ошибки), `content_log.txt` (скорость и ошибки загрузок),
  `cef_log.txt` (магазин/сообщество во встроенном браузере); пробы: https к магазину и сообществу,
  websocket CM, скачивание 500 КБ с CDN; DPI 16–20 КБ.
- Новый встроенный профиль `steam`.

### Dead by Daylight
- Причины: бэкенд `*.bhvrdbd.com` (TLS), EOS/EAC (`*.epicgames.dev`, `*.epicgames.com`), матч по UDP на
  серверы AWS; высокий пинг из-за маршрута через VPN; игровой фильтр zapret не покрывает порты матча.
- Журнал игры (`%LOCALAPPDATA%\DeadByDaylight\Saved\Logs`) зашифрован и не читается — опираться на сеть.
- Собрать: SNI и SYN к бэкенду; UDP-потоки матча и **RTT по каждому пути** (для игр важна задержка, а не
  только «отвечает»); совпадение портов матча с `game-filter`; правило роутера для процесса игры.
- Вывод: для игр `best_paths` ранжируется по RTT, жалоба «пинг 120» становится целью
  (`--goal latency`).

### Любая программа
- Наблюдение + SNI + признаки потоков; DPI 16–20 КБ к её TLS-хостам; покрытие списками; правила роутера;
  системные проверки. Журналы неизвестны — в выводе честно `client: unknown`.

## 4. Общие сигналы для всех профилей

- **Скорость и паузы по потоку** (байты/с, самая длинная пауза), а не только «ответил/нет»: торможение без
  обрыва сейчас выглядит как успех.
- **RTT по путям** для игр и голоса.
- **Сравнение с прошлым отчётом** того же профиля: «вчера работало» → что изменилось (стратегия, список,
  правило, версия Flowseal, обновление программы).
- **Провайдер и внешний IP** напрямую и через прокси: мобильный «белый список», смена провайдера.
- **IPv6**: есть ли, идёт ли туда трафик программы мимо zapret.
- **Ошибки самого хаба** за сутки (WinDivert, службы) — без этого вчерашний сбой WinDivert выглядел бы как
  поломка сети.

## 5. Порядок работ (предложение)

1. **Ложные выводы** (дёшево, обязательно): правило «один в канале»; «потери» на тихом UDP; «чисто» →
   «не определено», когда трафик через прокси не виден или голосового потока не было; голос против
   демонстрации; UDP через прокси.
2. **Вывод для агента**: компактный вид, коды итога и улик, уверенность, `fixes[].cli`, `next_steps`,
   отказ до наблюдения, разбивка оценки по пробам.
3. **Журналы клиентов**: стадия голоса и `discord-webrtc` (Discord), журналы Steam, журнал обновлятора.
4. **Пробы**: «как сейчас» первой и долгой пробой с остановкой группы; группировка приёмов по действию;
   DPI 16–20 КБ и замер скорости; `wss` голоса и шлюза; RTT для игр.
5. **Профили**: `discord-stream`, `steam`; DbD — по RTT; покрытие списками и возраст списков; сравнение с
   прошлым отчётом.

Каждый пункт 1–2 укладывается в существующие типы (`Summary` с заполнением при загрузке, компактный вид —
только в CLI). Пункты 3–5 добавляют парсеры и пробы в `crates/diag`, `crates/probe` и встроенные профили.
